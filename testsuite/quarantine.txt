# 这些用例与「本次改动」无关，但因为断言过时 / 依赖已清理的旧工具 / 环境差异而失败。
# 门禁默认不跑它们，但会反向检查它们是否「意外转绿」——转绿即报错，
# 强制有人回来把它们移出隔离区，避免隔离区变成垃圾场。
#
# 格式：<模块名>    # <原因>
#
# 前置条件：跑门禁的解释器必须装好 requirements.txt 里声明的依赖
# （至少 Jinja2 / packaging / flask）。缺依赖会让 8 个用例**假红**
# ——实测装上后 8/8 全绿，那不是代码问题。本机 pip 无法直连索引时，
# 可借 venv 的 pip 代装：
#   <venv>/Scripts/pip.exe --python <门禁解释器/python.exe> install Jinja2 packaging flask
#
# 维护纪律（第三轮审计的结论，32 → 6 → 5 → 0）：
#   1. 「隔离」不等于「不用管」。每条都要**两种跑法都试**——
#      `python -m unittest testsuite.<mod>` 与 `python testsuite/<mod>.py`。
#      脚本式用例在 `-m unittest` 下永远只给 `Ran 0 tests ... OK`，
#      只看这个数字会把「其实全绿」的模块误判成「导入失败」而长期挂在名单里。
#   2. 断言失败先分清是哪一种，再决定改测试还是改产品：
#      (i) 键/串从未存在  (ii) 已搬走（改名/移进模板）  (iii) 还在，但在另一个命名空间。
#      错判会让「测试取错命名空间」被当成产品缺陷。
#   3. 下面每一条都必须是**产品决策**，不能靠改断言绕过。
