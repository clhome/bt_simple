# 组件生命周期与安全响应政策

> 适用范围：御风面板（BtSimple）**通过插件托管 / 安装的第三方服务端组件**。
> 面板自身的漏洞报告流程见仓库根目录的 [SECURITY.md](../SECURITY.md)，
> 本文件只讲「被托管组件」的维护期口径与 EOL 处置，以及与安全基线表的关系。
>
> 状态：生效中（口径与代码现状对齐，代码位置见每节末尾的「实现位置」）。

---

## 1. 为什么需要这份政策

面板的插件能以 root 身份替用户编译 / 安装 PHP、MySQL、MariaDB、Nginx-OpenResty、Redis、
PostgreSQL。这意味着：**面板的版本列表事实上定义了用户的安全下限**。
如果面板仍然把上游已停止维护的版本摆在列表里、点一下就装，那么用户得到的不是「老版本兼容」，
而是一个永远不会再收到补丁、且面板还替他背书的服务。
所以本政策的底线是：**上游不修 → 面板不再默认提供；确需使用必须显式「自担风险」放行。**

## 3. 维护期口径

1. **仍在支持（Supported）**：上游仍在为该分支发布安全版本；面板保留在 `info.json`
   的 `versions` 里，可一键安装 / 升级，并随上游安全版滚动更新安装脚本里的版本号与
   sha256 校验值。
2. **安全回移期（Backport-only）**：上游该分支已不再发新版本，但发行版（Debian / Ubuntu /
   sury / RHEL / Remi）仍在出安全回移补丁。此时**只用渠道包**（APT / YUM 插件）提供，
   不再提供源码编译版 —— 因为编译版拿到的是死源码。
3. **终止支持（EOL）**：上游与下游发行版都不再出补丁。
   - 从 `info.json` 的 `versions` 中**下架**，默认不可安装；
   - 存量安装不受影响（`uninstall` / `stop` / `restart` 等动作仍然可用），
     避免用户被「政策」锁死在一台起不来的机器上；
   - 面板的安全基线扫描（`web/core/php_sec_baseline.py`）会把这类分支直接判定为高危。

## 4. EOL 后的处置：下架默认路径 + 「自担风险」显式放行

处置分两类，**文案与提示不得混用**（混用会让用户以为是同一个风险等级）：

### 4.1 类 A：存在已知未修复漏洞 → 默认拒绝，公网禁用

例：PHP 5.2 ~ 7.3（含 CVE-2026-109618 / CVE-2026-109619 一类**官方不会修**的漏洞）。
处置：`install` 动作直接 `exit 1`，只有显式设置 `YF_ALLOW_UNSAFE_PHP=1` 才放行，
且放行时再打印一次风险警告（「仅限隔离 / 内网、切勿暴露公网」）。

### 4.2 类 B：编译版下架 → 改走 APT / YUM 渠道

例：PHP **7.4 / 8.0 / 8.1**。上游源码树不再出安全版，但发行版仍有安全回移补丁。
处置：编译版（`plugins/php/`）的 `install` 动作默认拒绝，提示改用
`plugins/php-apt/`（Debian / Ubuntu + sury）或 `plugins/php-yum/`（CentOS / RHEL + Remi）。

### 4.3 现状对齐（写这份政策时的代码事实）

- `plugins/php/info.json` 的 `versions` 只剩 **82 / 83 / 84 / 85**（其余已下架）；
- `plugins/php/install.sh` 的拦截清单：
  类 A = `52 53 54 55 56 70 71 72 73`，类 B = `74 80 81`，统一由
  `YF_ALLOW_UNSAFE_PHP=1` 显式放行；
- APT / YUM 插件的 `versions` 仍保留 74 / 80 / 81（它们是有回移补丁的安全路径）。

**实现位置**：`plugins/php/install.sh`（拦截逻辑）、`plugins/php/info.json`（版本下架）、
`plugins/php-apt/info.json` / `plugins/php-yum/info.json`（渠道路径）。
**门禁用例**：`testsuite/test_php_unsupported_versions.py`。

## 5. 高危 CVE 响应 SLA（与 SECURITY.md 数字一致）

| 阶段 | 承诺时限 |
| --- | --- |
| 确认受影响组件 / 分支范围并对外说明 | **≤ 72 小时** |
| 给出**缓解方案**（禁用某分支、切换到渠道包、临时配置加固等） | **72 小时内** |
| 发布**修复版本**（面板发版或插件版本号滚动） | **14 天内** |

补充约定：

- 「修复」有两种形态，都算数：①发布新面板版本更新安装脚本 / 基线表；
  ②插件内滚动到上游安全版本并更新 sha256 校验值；
- 若 14 天内无法完成，必须在 Release 说明或 Advisory 里写明原因、当前可用缓解措施与新的预计时间；
- 只影响 EOL 分支、且已按第 4 节下架 / 标注「自担风险」的漏洞，**不承诺修复**，
  只按上表第一行给出「影响范围说明」。

## 6. 与安全基线表（`BASELINE_DATE`）的关系

`web/core/php_sec_baseline.py` 内置一张 PHP 安全基线表，`BASELINE_DATE` 是**这张表的取值日期**
（当前为 `2026-10-22`）。两者是「政策」与「执行」的关系：

1. **基线表是政策的执行侧**：第 3 节的维护期判定、第 4 节的 EOL 分级，最终都体现为
   基线表里的「分支 → 最低安全小版本」与「分支是否直接判危」；
2. **基线表必须随官方安全版滚动更新**：上游每发一次安全版，就要同一次提交里上调
   `BRANCH_BASELINE` 的基线版本 **并** 刷新 `BASELINE_DATE`；
   只改版本不改日期会让面板的「基线已过期」判断失真；
3. **过期即告警**：基线日期超过一定时限未更新时，面板的安全检查会给出「基线过期」提示
   —— 这是**故意**的，提示维护者去核对上游是否有新安全版，而不是让用户以为「没告警 = 没问题」；
4. 基线表是**离线内置**的（面板不做网络请求），因此「更新基线」= 发版；
   这也是第 5 节 SLA 里「14 天内出修复版本」能成立的前提。

**实现位置**：`web/core/php_sec_baseline.py`（`BASELINE_DATE` / `BRANCH_BASELINE` /
`OFFICIAL_SHA256`）、`web/core/php_sec_scan.py`（扫描与提示）。
**门禁用例**：`testsuite/test_php_security_baseline.py`。

## 8. 依赖与 Python 版本支持

面板自身的 Python 依赖（`requirements.txt`）里保留了一组 **`python_version < '3.9'` 的过渡分档**，
与「被托管组件」不同：它管的不是用户装的服务，而是**面板自己能不能在这台机器上装起来**。

### 8.1 保留哪些分档（4 处，与依赖文件一一对应）

| 依赖 | `python_version >= '3.9'` | `python_version < '3.9'` |
| --- | --- | --- |
| `flask` | `>=3.1.3,<4.0.0` | `>=2.0.3,<3.0.0` |
| `Werkzeug` | `>=3.1.6,<4.0.0` | `>=1.0.1,<3.0.0` |
| `pyOpenSSL` | `>=26.4.0,<27` | `==26.0.0` |
| `cryptography` | `>=50.0.0,<51` | `>=40.0.2` |

### 8.2 为什么还没删

因为面板**仍然要能装在 CentOS 7 与 Debian 10 上**：这两个发行版自带的 `python3` 是
**3.6 / 3.7**，低于 3.9，装不了 `flask 3.x` / `Werkzeug 3.x` 这条新线。删掉过渡分档会让
这两类存量机器**直接装不上面板**（`pip` 解析阶段就失败），而不是「装个旧版还能用」。
所以它们是**兼容垫片**，不是「忘了升级」。

### 8.3 EOL 时间与移除动作

**`python_version < '3.9'` 全部分档的 EOL 日期是 2027-06-30**。到期后的动作：

1. 从 `requirements.txt` 移除全部 4 处 `python_version < '3.9'` 分档，
   面板最低支持版本提升到 **Python 3.9**；
2. 同步更新本节与 `SECURITY.md` 的「已知取舍」；
3. 在 Release 说明里写明「不再支持 CentOS 7 / Debian 10 默认解释器」，
   并给出升级 Python 或改用渠道包的建议。

门禁会拦住「提前删」：`testsuite/test_requirements_bounds.py` 的
`test_05_py39_branches_still_four` 断言这 4 个分支必须仍在（移除必须等到 2027-06-30）。

### 8.4 已知残留风险（明确不承诺修复）

- 过渡分档锁定的都是**上游已停止维护的版本**（`flask 2.0.x` / `Werkzeug 1.x` /
  `pyOpenSSL 26.0.0` / 更老的 `cryptography`），它们的已知 CVE **不会再收到官方修复**，
  面板也不会为它们回移补丁；
- 这类风险属于**已知残留风险**，在「承诺修复」范围之外（对照第 5 节的 SLA：
  只影响 EOL 分支、且已按第 4 节标注「自担风险」的问题，只给影响范围说明）；
- 风险面收敛的前提是：这些库只被面板**本地进程**使用，面板不把它们作为对外服务暴露；
  一旦出现「面板把依赖版本透传给用户站点」的用法，本节的结论必须重评。

**实现位置**：`requirements.txt`（4 处带 `python_version < '3.9'` 的分档行，行尾注释写明
「计划于 2027-06-30 停止支持」与「下界取自开发环境实测版本」）。
**门禁用例**：`testsuite/test_requirements_bounds.py`（`test_05` / `test_06` / `test_07`）。

## 9. 技术债偿还计划

本节管的是**面板自己的命令构造技术债**（shell 拼接），与第 3 节的「被托管组件版本」无关，
但同样是「不修就会一直烂下去」的那类问题：`web/core/yf/__init__.py` 的 `execShell` /
`execShellRc` 历史上默认 `shell=True`，调用点把用户输入直接拼进命令字符串，形成了存量
shell 裸拼。只做「只减不增」的棘轮只能证明**没变坏**，证明不了**会变好** —— 基线一旦不再
缩小，存量裸拼就变成永久豁免。因此本节给出**带日期、带上限数字**的下降曲线。

### 9.1 新代码口径（先止损）

1. **新代码默认必须用 argv 列表 + `shell=False`**：argv 不经过 `/bin/sh` 重新解析，
   参数里的空格、引号、`$()`、反引号都不会被解释 —— 这是唯一「参数带外部输入也安全」的形态；
2. 只有命令**本身真的需要 shell**（`cd` / `export` / `source` 等内建、管道、重定向、
   `&&` / `;` 串联），**且参数不含任何外部输入**（全是常量，或已过 `yf.shlexQuote()`）时，
   才允许 `shell=True`，并且必须在**该调用点就地**注释理由；没有理由注释的 `shell=True`
   调用点按违规处理；
3. 需要判成败（「脚本失败」不能与「脚本无输出」混淆）时用 `execShellRc` 拿退出码，
   不要用 `execShell` 的空输出当失败。

### 9.2 存量下降档位（写死的上限，不在断言里现算）

| 截止日期 | `web/` 允许上限 | `plugins/` 允许上限 | 说明 |
| --- | --- | --- | --- |
| 2026-10-22 | 81 | 316 | 基线快照日（实测值 = 两份基线文件的条目数） |
| 2027-06-30 | 57 | 221 | ≈ 基线的 70% |
| 2027-12-31 | 32 | 126 | ≈ 基线的 40% |
| 2028-06-30 | 0 | 0 | 终点：存量清零，基线文件只允许剩注释 |

判定口径：取**最后一个「截止日期 ≤ 今天」的档**作为当天生效的上限（到期日当天即生效，
并一直约束到下一个到期日）；今天早于第一档时取第一档（只有更严，不会更松）。
因此 2028-06-30 那一天起上限就是 0，闸门必然收紧。

### 9.3 与代码/门禁的对应关系

- 基线文件：`scripts/shell_concat_baseline.txt`（web 段）、
  `scripts/shell_concat_baseline_plugins.txt`（插件段）；
- 计划表唯一事实来源：`testsuite/test_shell_concat_ratchet.py` 的 `REDUCTION_PLAN`
  （四档，与 9.2 表格逐值一致，改表必须是一次显式人工提交）；
- 新代码检查点：`testsuite/test_shell_debt_reduction_plan.py` 对「未跟踪新文件 +
  相对 HEAD 的改动文件」跑静态检查，基线之外的新增裸拼直接报红；
- **`execShell` / `execShellRc` 的 docstring 明确指向本节**（「下降档位与到期日见
  《组件生命周期与安全响应政策》第 9 节」），因此本节被删除会让代码注释变成断链。

## 10. 升级需知：cron 任务标识白名单

计划任务的「任务标识」在数据库里是 `crontab` 表的 `echo` 列，它同时扮演两个角色：

1. 脚本文件名：`/www/server/cron/<echo>`（以及 `<echo>.log`）；
2. 被拼进 root 的 crontab 行（`/var/spool/cron/crontabs/root`）。

所以它**不是**自由文本。判据只有一个：`web/utils/crontab.py` 的 `_CRON_NAME_RE`
（`^[A-Za-z0-9_.-]{1,64}$`）—— 即 **cron 任务标识白名单**，由 `_cron_safe_name()` 执行。
含空格、分号、换行、路径分隔符等字符的值一律拒绝：换行/分号会往 root 的 crontab 里
追加任意计划任务，斜杠会写到 `cron/` 目录之外。

### 10.1 升级时会遇到什么

白名单上线**之前**，`init_cron` 恢复「其它系统任务」时会把**原始命令**写进 `echo`。
这类历史任务在升级后会出现：

- 列表接口返回 `sync_ok = False`、`sync_reason_code = cron_name_invalid`、`sync_reason`
  为指引文案；前端在任务名旁显示「同步被拒」标记（鼠标悬停看原因），
  不会再让人误以为任务还在正常跑；
- 这些任务**同步到 crontab 会被拒绝**（此前是静默拒绝、只留一条日志，用户完全看不到
  它已经停摆）。

### 10.2 怎么修（用户侧动作）

打开该任务的**编辑**弹窗，把「任务标识」改成合规值（字母/数字/下划线/点/短横线，≤64），
然后**重新保存**。保存动作本身也会兜底：若 `echo` 仍不合规，写入时会自动换成新的
合规标识，并先删掉旧标识对应的 crontab 行，不需要用户手工清 crontab。

> 注意：**升级本身不会自动改历史任务的标识**（那会让「任务名 → 脚本文件 → 日志」
> 三者对不上，还可能误删别人的 crontab 行）。是否批量迁移属产品决策，当前口径是
> 「暴露问题 + 引导重新保存」。

**实现位置**：`web/utils/crontab.py`（`_CRON_NAME_RE` / `_cron_safe_name()` /
`cron_name_status()` / `CRON_SYNC_REASON_NAME_INVALID`）、
`web/static/app/crontab.js`（同步被拒标记）。
**门禁用例**：`testsuite/test_crontab_sync_status.py`。

## 11. 附录：PHP `cgi.fix_pathinfo` 的处置结论

**结论：`cgi.fix_pathinfo` 保留默认值 `1`，不改 0。**

依据（这也是「保留默认值」之所以安全的前提）：

1. 站点 vhost 模板（`web/misc/nginx/tpl/nginx.conf`）会 `include enable-php-{$PHPVER}.conf`；
2. 三个渠道（`plugins/php/`、`plugins/php-apt/`、`plugins/php-yum/`）的
   `conf/enable-php.conf` 里，PHP 定位块是 `location ~ [^/]\.php(/|$)`，
   并且**第一行就是 `try_files $uri =404`**：
   **不存在的 `.php` 路径在 nginx 层直接 404**，请求根本到不了 php-fpm；
3. 因此 PHP 侧「`fix_pathinfo=1` 时沿路径向上回退找已存在文件」这条被利用的链路
   **永远不触发**（不存在的 `/upload/x.jpg/a.php` 在 nginx 就被拦掉）；
4. PATH_INFO 的拆分用 `if ($fastcgi_script_name ~ "^(.+?\.php)(/.+)$")` 的等价写法
   （见 `plugins/php/conf/pathinfo.conf`），不依赖 `fix_pathinfo` 的回退行为。

**什么情况下必须重评**：一旦有站点模板不再 `include enable-php-{$PHPVER}.conf`、
或把 `try_files $uri =404` 从 PHP 定位块里摘掉，`fix_pathinfo=1` 就不再安全 ——
此时必须把三渠道的默认值改 0，并同步本节与对应注释。

**实现位置**：`plugins/php/index.py`（`makePhpIni()` 与两处 `defaults_map`，各渠道共 9 处
`'cgi.fix_pathinfo': '1'`）、`plugins/php{,-apt,-yum}/conf/enable-php.conf`。
**门禁用例**：`testsuite/test_p2_16_misc.py`（默认值、理由注释、`try_files` 兜底三者互相交叉校验）。
